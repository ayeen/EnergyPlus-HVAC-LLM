The Challenge

Why Automate HVAC Design?

Manual HVAC configuration for EnergyPlus is time-consuming, error-prone, and requires deep domain expertise.

⏱️

Time-Consuming

Manual VRF system configuration requires specifying 42 fields per system, plus zone-level objects and thermostats. A 20-zone building can take hours to configure correctly.

❌

Error-Prone

Field value mismatches, missing references, invalid enumerations — even experienced engineers make syntax errors that cause simulation failures.

📚

Domain Expertise Required

EnergyPlus has 900+ object types with complex interdependencies. Understanding VRF field specifications requires years of HVAC engineering experience.

💡

Our Solution

A multi-agent AI system that takes natural language descriptions and produces complete, simulation-ready EnergyPlus IDF files — with built-in error correction.

Architecture

Multi-Agent System Architecture

🔑 Design Principles

  • Separation of Concerns — each agent specializes
  • Iterative Refinement — mimics engineering workflow
  • Knowledge-Enhanced — RAG provides runtime context
  • Bounded Execution — max 3 correction iterations

📡 Agent Communication

JSON-based protocol: Agent 1 sends HVACTemplate objects → Agent 2 validates & simulates → Agent 3 receives error messages + IDF path → Returns targeted JSON fix specifications.

🏗️ VRF Architecture

1 outdoor unit serves N indoor units (one per zone). The system generates all HVACTemplate objects that EnergyPlus ExpandObjects converts to detailed simulation objects.

Agents 2 & 3 — Validate & Correct

Four-Stage Validation + Iterative Correction

✅ Agent 2: Validation Pipeline

Stage 1 IDD Compliance Check

Validates object types, required fields, value ranges against EnergyPlus Data Dictionary

Stage 2 Eppy Validation

Cross-object reference checking, zone links, schema compliance using Eppy library

Stage 3 ExpandObjects

HVACTemplate → Detailed objects (coils, fans, schedules, piping, controls)

Stage 4 EnergyPlus Simulation

Full energy simulation, parses eplusout.err for errors → classifies: Warning / Severe / Fatal

🔧 Agent 3: Error Correction

Correction Strategy

1 Receive error messages from Agent 2
2 Query RAG for similar error patterns
3 If similarity > 77% → Apply cached fix
4 Otherwise → LLM generates JSON fix spec
5 Apply fix via Eppy → Re-simulate

🚀 Fine-tuned: No Degradation

Maintains 100% quality from 1 to 20 zones. The iterative generation strategy handles scaling by generating objects per-zone sequentially.

⚠️ Pre-trained: Breaking Point at 20

Quality degrades progressively: 100% at 1 zone → ~35% at 10 zones → 0% at 20 zones. Token window overflow causes missed zones and malformed objects.

💡 Why Fine-tuning Matters

Domain knowledge is encoded in weights, not in prompts. Fine-tuned models don't need extensive context — they inherently know VRF field specifications, reducing token usage and improving reliability at scale.

✅ RAG Enhances Fine-tuned (+5%)

RAG improves edge case handling — retrieving specific field specifications and dependency rules that prevent subtle errors.

❌ RAG Cannot Rescue Pre-trained

Pre-trained models with RAG still fail at 80%. RAG provides context but cannot teach the model the VRF generation format and syntax.

💡 Conclusion

Fine-tuning is essential. RAG is beneficial as a complement but not as a substitute. The best results come from combining both technologies.
